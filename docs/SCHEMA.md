# Database schema (BrainX V5)

Source of truth: [`sql/v3-schema.sql`](../sql/v3-schema.sql)

BrainX V5 uses PostgreSQL tables prefixed with `brainx_`.

> Prerequisite: `CREATE EXTENSION IF NOT EXISTS vector;`

## Table: `brainx_memories`

The main memory store.

### Purpose

Stores atomic memory items (decisions, actions, notes, learnings, etc.) plus metadata used for retrieval.

### Columns

- `id` (text, PK)
  - caller-provided or auto-generated by the CLI.
- `type` (text)
  - must be one of: `decision | action | learning | gotcha | note | feature_request`
- `content` (text)
  - the text payload.
- `context` (text, nullable)
  - exact-match scope key. Examples:
    - `openclaw`
    - `emailbot`
    - `workspace-coder/MEMORY.md`
- `tier` (text, default `warm`)
  - `hot | warm | cold | archive`
- `agent` (text, nullable)
  - which agent/system wrote it.
- `importance` (int 1..10, default 5)
  - used for ranking.
- `embedding` (`vector(1536)`)
  - vector embedding used by pgvector. **Must match** `OPENAI_EMBEDDING_DIMENSIONS`.
- `created_at` (timestamptz)
- `last_accessed` (timestamptz)
- `access_count` (int)
  - access tracking updated on search.
- `source_session` (text, nullable)
  - intended to link to a conversation/session id.
- `superseded_by` (text, nullable)
  - points to the “kept” memory when this one is superseded/deduped.
- `tags` (text[])
- `verification_state` (text, default `hypothesis`)
  - retrieval trust level:
    - `verified` → memory can safely influence operational decisions
    - `hypothesis` → plausible but not yet trustworthy enough to outrank live evidence
    - `changelog` → historical/reporting value, not decision authority
    - `obsolete` → excluded from retrieval

### Indexes

- `idx_mem_embedding` — ivfflat on `embedding` (cosine)
- `idx_mem_tier` — `(tier, importance desc)`
- `idx_mem_context` — `(context)`
- `idx_mem_tags` — GIN index

### Notes

- Queries exclude superseded memories via `WHERE superseded_by IS NULL`.
- Dedup is implemented by setting `superseded_by` and tagging the old rows.

## Table: `brainx_learning_details`

Optional structured details for `learning` memories.

### Purpose

Captures “post-mortem” / debugging fields that are hard to consistently fit in plain text.

This table is not yet written by the CLI, but the schema supports it.

### Key columns

- `memory_id` (PK, FK → `brainx_memories.id`)
- `category`
- `what_was_wrong` / `what_is_correct`
- `source`, `error_message`, `stack_trace`
- `command_attempted`
- `related_files` (text[])
- `complexity` (`simple|medium|complex`)
- promotion fields: `promotion_status`, `promoted_to`, `promoted_at`

## Table: `brainx_trajectories`

### Purpose

Stores “how we solved it” multi-step solutions as reusable trajectories.

- `steps` is `jsonb`.
- Has its own `embedding` and `times_used` counter.

## Table: `brainx_context_packs`

### Purpose

Stores larger “packed context” blobs (`data` as `jsonb`) generated by the daily maintenance wrapper.

The `embedding` column is reserved for future semantic retrieval; current runtime retrieval does not read context packs. The builder upserts stable IDs by context/window so future runs do not accumulate duplicate generated rows.

## Table: `brainx_runtime_injections`

### Purpose

Stores runtime evidence-injection telemetry from the BrainX plugin.

Important columns:

- `agent`
- `session_id`
- `session_key` — persisted delivery/session scope for DB-backed scoring fallback
- `surface` — `jit_recall`, `recovery_preflight`, `working_memory`, or `wiki_digest`
- `memory_ids`
- `selected_count`
- `referenced_count`
- `soft_referenced_count`
- `decision_summary`
- `scored_at`

Selected rows should be scored by `llm_output` or scoring-only `message_sent`. If no visible answer arrives, the health wrapper finalizes stale selected rows with zero references instead of leaving telemetry indefinitely unscored.

## Table: `brainx_session_snapshots`

### Purpose

Stores session-level summaries, status, blockers and pending items.

Useful for: resuming work after long gaps.

## Table: `brainx_artifact_ledger`

### Purpose

Stores durable/recoverable artifact paths for runtime recovery.

Important columns:

- `artifact_path` — absolute path to the candidate artifact
- `artifact_kind` — coarse file type (`document`, `image`, `archive`, etc.)
- `artifact_role` — semantic role (`final_deliverable`, `generated_asset`, `screenshot_evidence`, `report`, `referenced_file`, `temp_candidate`)
- `provenance` — capture source (`promoted_handoff`, `assistant_final`, `tool_write`, `tool_read`, `tool_exec`)
- `finality_score` — ranking score used by recovery so final artifacts outrank temp/read/exec noise
- `metadata` — JSON audit details

## Table: `brainx_context_state`

### Purpose

Stores compact latest state by `agent + session_key`.

This is the deterministic handoff surface used when OpenClaw rotates `sessionId` but the Discord/channel `session_key` stays the same.

Important columns:

- `runtime_family`
- `turn_intent`
- `last_user_prompt`
- `last_assistant_output`
- `last_artifact_path`
- `last_artifact_role`

## Table: `brainx_session_rotation_events`

### Purpose

Stores observed OpenClaw `sessionId` rotations by `agent + session_key`.

This is the audit surface for whether BrainX detected a rotation, forced recovery, and injected the compact handoff block.

Important columns:

- `previous_session_id`
- `current_session_id`
- `triggered_recovery`
- `injected_handoff`
- `missed_reason`
- `runtime_family`
- `metadata`

## Table: `brainx_pilot_log`

### Purpose

Stores telemetry from the auto-inject hook (`hook/inject.sh`). Each agent bootstrap logs what was injected.

### Columns

- `id` (serial, PK)
- `agent` (varchar(50)) — agent name that received the injection
- `own_memories` (integer, default 0) — count of agent-specific memories injected
- `team_memories` (integer, default 0) — count of high-importance team memories injected
- `total_chars` (integer, default 0) — total characters written to BRAINX_CONTEXT.md
- `injected_at` (timestamptz, default NOW()) — when the injection happened

## Operational considerations

### pgvector and ivfflat

- ivfflat indexes require `ANALYZE` and enough rows to be useful.
- You may want to tune `lists` per table size.

### Dimension changes

If you change `OPENAI_EMBEDDING_DIMENSIONS`, you must also:

- change `vector(1536)` in schema
- rebuild embeddings for existing rows

### Backups

A standard Postgres backup is enough (e.g. `pg_dump`).
